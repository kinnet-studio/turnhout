# Startup Simulator Long Runs Speed-up 4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `src/games/startup-simulator.test.ts` runs about 11% faster (its vitest `tests` figure, best of round, from about 26 s to about 23 s, and a third less CPU), with byte-identical behaviour, so that plan 7-2b's Veto window (about +4 s) still leaves it under 30 s.

**Architecture:**
- Plan 7-2a's ledger ruled R29(d): its head's best was 38.1 s against 28.4 s before it, over the 30 s watch, so this speed-up runs before 7-2b.
- The profile is `docs/superpowers/notes/2026-11-23-startup-speed-4-proposal.md` (scratchpad `perf4/`). It found two causes:
  - **V8 recompiles two giant functions whole:** the long runs' rules check (one closure, 48 sections) and `happenings`. A move that reaches a new path deopts the whole function, and TurboFan spent 49.4 s on them.
  - **Half the values about a player are asked again of the same state** (51% repeats), and each is worked out afresh.
- Four changes, measured together on 5d500b6 as `perf4/candidates/set-on-wave.diff`:
  - **E1** (engine): `LangRuntime.playerValue` keeps what each value came to per state object, in a `WeakMap<GameState, Map<string, number>>`. It looks the value up inside `workOut`, so a value asked while it is worked out still throws. Nothing is kept or read while the checker answers. A value whose lines threw keeps nothing.
  - **T1** (test file, generated by `perf4/tools/split-iterate.py`): each section of the rules check and of `happenings` becomes an arrow function called in place, in the same order. A section that declares names a later one reads returns them: `const { a, b } = rulesPart9();`.
  - **T2** (test file): an `investing()` memo.
  - **T3** (test file): the Board and Equity checks read places once per move.
- The patch applies to this plan's BASE as it is (`git apply --check` passes on c87027d). Apply its hunks per task; do not retype them.

**Tech Stack:** TypeScript, vitest.

**Spec:** the overview, `docs/superpowers/specs/2026-10-16-startup-simulator-overview-design.md`. Its proof is long runs at 2–5 players that check the rules after every move. This plan changes no behaviour, so the spec's rules bind only as "nothing changes".

## Review Focus

## Gaps

- **Later plans and the split.** The test file is committed split, and later plans keep it so:
  - A new check goes inside the section it belongs to.
  - A name a later section reads is added to that section's `return { … }` and to its caller's `const { … }`.
  - A new section may stand unwrapped in the outer function.
  - A later speed-up can wrap new sections by hand, in the same shape. `split.py` is written for the unsplit file: run on the split one, it wraps again (checked on `perf4/wave`), so it must not be rerun as it is.
  - The handoff's Notes carry this.
- **E1's rule for later plans:** a phrase that a value about a player can reach must read only what `env` gives it. A phrase that reads anything else, such as a runtime field or a value outside the state, would be kept stale. The handoff's Notes carry this too.
