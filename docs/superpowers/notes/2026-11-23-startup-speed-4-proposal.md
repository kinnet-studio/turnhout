A scratch clone at c8c7a88 (`perf4/work`, `node_modules` linked from the repo), with dbb2f34 (`perf4/base0`) for the time before 7-2a.
Nothing here touched `/home/user/turnhout`. Every figure is vitest's `tests` figure for `src/games/startup-simulator.test.ts` alone
unless it says otherwise; "BASE" is an unchanged c8c7a88 worktree (`perf4/base`) run in turn with the others.

`seen=m` the most counted by a sample every 2 s during it (one vitest job is 3–4 processes). The deterministic counters (moves, phrase
calls, worked-value and player-value calls) and the CPU seconds (`cpu=`, vitest and its worker, user+sys) stand beside every wall-clock
figure.

**(a) V8 recompiles the two largest functions again and again.** `tools/trace-opt.sh` runs the file with `--trace-opt

| TurboFan, the 2-player long run alone | dbb2f34 | c8c7a88 |

### 2.1 T1: one function per section of the rules check and of `happenings` (test file; generated)

**What it changes.** `tools/split.py` cuts the closure `keepsTheRules` returns and `happenings` at their top-level comments, the
same sections `tools/instr2.py` times. Each section becomes an arrow function called in place, in the same order:

```ts
    // An Invest, the one that places a Consultant too, moves exactly its card, …
    const rulesPart10 = () => {
      if ([INVEST, INVEST_PLACING].includes(move.type)) { … }
    };
    rulesPart10();
```

A section that declares names a later section reads returns them, and the caller declares them again: `const { equityProblems,
stray } = rulesPart9();`. 42 of the rules check's 47 sections and 9 of `happenings`' 10 are wrapped. With whitespace ignored the diff
is 171 added lines and no other change (`git diff -w master t1`: 51 `const …Part = () => {` lines, their `};`, their calls and returns).

**Why it is safe.**
- The same statements run in the same order with the same values: each wrapped section runs once, at the place it stood, and reads
  the names before it through its closure.
- `split.py` wraps a section only when it has no top-level `return`, `continue`, `break` or `yield`, and every name it declares that
  is read elsewhere is a `const`. A section that declares a `let` read later stays as it is.
- `tools/split-iterate.py` typechecks the result and keeps out what tsc rejects: two sections (39 and 41) whose `let` the outer
  function narrows, which a closure would not see narrowed, and ten names tsc reported never read once returned (a later section
  declares its own of the same name; `tools/split-opts.json`).
- Every check builds its message as before. Only a stack trace changes: it names the section (`rulesPart10`), one frame deeper.

**Why it wins.** The compile units are now 51 small functions. A move that reaches a new path deopts only its section, which
recompiles in milliseconds, and the closure that calls them is a short list of calls. Measured by `trace-opt.sh` over the whole file (`logs/trace-opt-{base,t1,set}-all.txt`):

| TurboFan, whole file | c8c7a88 | t1 | set |
|---|---:|---:|---:|
| compile time, all functions | 49.4 s | 9.2 s | 11.0 s |
| compiles / deopts | 1404 / 257 | 1539 / 361 | 1514 / 350 |
| the dearest function | the rules closure, 24.6 s (22×) | `rulesPart14`, 0.67 s (12×) | `rulesPart14`, 0.70 s (11×) |

There are more deopts, but each costs a section's compile, not the whole check's. The CPU the file uses falls by a third (§2.5:
58.9–68.7 s for c8c7a88, 38.5–42.4 s for t1), because the background compiles were most of it.

**Porting over the fix wave.** Nothing to port by hand: rerun `python3 tools/split-iterate.py <worktree> <opts.json>` on the new
file (a few minutes), from an empty options file, since the section numbers shift. Done on 5d500b6 (§4.1): one section more (48), the
same two sections kept unwrapped (now 40 and 42), one more name not returned (`tools/split-opts-wave.json`), tsc clean. The wave's new checks (the Consultants counted from `othersOn` and the colour flags; the colour just
chosen checked on each placement) land inside existing sections; a new top-level comment just makes one more section. If tsc rejects a
new section, split-iterate keeps it unwrapped and says so.

**Risk: low.** The diff is large but mechanical, and a reviewer reads it with `-w`. The one way it can go wrong is a section that
needs the outer function's narrowing, which tsc catches. Later plans keep writing sections as before; the split is regenerated, not
maintained. The cost is that the file's two big functions read as a list of sections, which is arguably clearer.

### 2.2 E1: keep what each value about a player came to in each state (engine; `runtime.ts`)

**What it changes.**
- `LangRuntime.playerValue` keeps the number it worked out in a `WeakMap<GameState, Map<string, number>>` (`ofState`), keyed by the
  state object, then by seat and name.
- The lookup sits inside `workOut`, so a value asked from itself still throws `WORKED_FROM_ITSELF` before anything is read.
- Only a number is kept: lines that throw keep nothing and throw again.
- While the checker answers a phrase (`check`, the only way a phrase reaches the engine's handlers: "they have no card they could
  play"), nothing is kept or read. A value asked there is worked out afresh, as before, so one that asks the checker again still throws
  `DEPEND_ON_EACH_OTHER`.
- 29 lines of engine code. The tests add three import lines of their own to `player-value-phrases.test.ts` (no existing import line
  is edited).

**Why it is safe.**
- **A value about a player is a function of the state.** Its lines get `env` from `this.env(state, undefined, undefined, { player:
  seat, … })`: the state, the compiled game, the seats and the runtime's own value functions. No move, no example, no subject card.
  The game and seats are fixed for a runtime, and the value functions are themselves functions of the state (the card values kept by
  card object, as before).
- **States never change once made.** The engine and every library function make a new state for every change; `grep` finds no
  assignment to a state's `cards`, `data` or `turn` anywhere in `src/` (`state.cards.push`, `state.data[…] =` and the like), and the
  existing card caches already rest on card objects and `state.cards` arrays never changing. A state is a WeakMap key, so a state no
  one holds any more takes its values with it.
- **The runtime's moving parts are left as they were.** The `workingOut` stack (a value asked from itself) is consulted before the
  lookup. The `checking` flag (the checker asked from inside itself) turns the keeping off, so a value read inside the checker is
  worked out exactly as before. Outside the checker, every value on the `workingOut` stack belongs to the same state (only `check`
  hands a phrase another state), so a value kept for that state could only skip a cycle that its own first working-out would already
  have thrown on, and then nothing was kept.
- **No shared word.** The code says "a value about a player", "state", "seat"; no Startup, veto, supply or partner. No protected file.

**Unit tests** (`player-value-phrases.test.ts`, 5 new; the file's 28 pass):
- a value is worked out once for a seat in a state (a spy on `call` counts nothing the second time), and another seat or another
  name in the same state is worked out for itself;
- a new state object, even with the same cards, is worked out afresh, and a state made by moving a card gets its own value while
  the old state keeps its own;
- seven states made one from another (sharing most of their cards) each keep their own 6 values, read again with no phrase call, the
  same as a fresh runtime gives;
- in the checker nothing is kept or read: the value's line runs on every check, before and after it was kept outside;
- a value about a player worked out from itself throws every time.
- Mutations of E1 itself: keeping by seat and name only (blind to the state) fails 4 tests, two of them older ones; keeping and
  reading inside the checker fails the checker test; no keeping at all (c8c7a88's runtime) fails three: the first, the many-states
  and the checker test.

**Why it wins.** It removes the 88,418 repeated calls of §1.3(b): `top tier`, `share price`, `operational revenue` and a third of
the supplies, wherever they are asked (the engine's guards and rules, the page's view, the auto-player, the rules check).

**Porting:** none. The fix wave does not touch `runtime.ts`; the patch applies to 5d500b6 as it is.

**Risk: low.** It is the same kind of cache as the card values' (`keptFor`), on an object the engine already treats as never
changing. The new rule a later plan must keep: **a phrase that a value about a player can reach must read only what `env` gives it,
and anything that is not the state must be fixed for the runtime.** A phrase that read, say, the move being made or a field the
runtime changes would break it. Today `env.check` is the only such path, and it is guarded.

### 4.2 Room for 7-2b: the Veto window's cost, estimated

Counted on c8c7a88's long runs, as if 7-2b were in (`stats-instr-base-r3.json`, the `veto:` counters `tools/instr2.py` adds to the
auto-player's moves): 2,148 of the 5,406 moves cost an action, and in 1,252 of them another seat held one of the mover's tokens, so
the window would open; 1,261 seats would be asked (1,243 windows ask one seat, 9 ask two). If each asked seat answers with one move
(pass or Veto), the long runs grow by **1,261 moves, +23%**.

- **At c8c7a88's cost a move** (19.9 s of long runs / 5,406 = 3.7 ms, quiet), that is about **+4.6 s** for the four long runs, plus
  about +1.0 s in the two replay tests (they replay the kept games' logs, 23% longer), plus the undo, Greenlight and view tests' share:
  **≈ +6 s** on a 31–32 s file.
- **canDispatch** adds little: answering a window is one or two canDispatch calls (pass, Veto), against 79,413 now at about 8 µs each.
- **At `set`'s cost a move** (about 2.5 ms: the long runs fell 31% from c8c7a88 to the set in `logs/verbose-{base,set}-2.txt`), the same moves cost **≈ +3.2 s in the long runs and ≈ +4 s in all**, and the file would stay below c8c7a88's time.
- A Veto that cancels the action also changes what the games do from there, so the move count is a first estimate, not a bound.
- The window moves are like the event check's confirms: cheap to apply, and dear only for the invariants every move runs. That is
  where T1 and E1 act.
